## Saving by text (added 2026-10-13, on the operator's word)

After a pastor's reply is delivered, the pastor is offered SAVE. "SAVE dress
code" writes that reply into Telechurch's saved answers
(`org_standing_answers`) as a standing answer for the church under that
subject, in the pastor's words only. A bare SAVE is asked for a subject. A
reply is saved once. Every question handed to the collector carries the
church's answers in force, read fresh, and the collector gives each one its
own second look ahead of the general cards.

**Ruled, no longer inferred.** The operator, 2026-10-13, relayed by the
phone-trial session and recorded in his words in the Telechurch phone-trial
record: "Yes save by text is the approval". A pastor's SAVE makes the answer a
standing answer at once. His yes carries one condition: the text must come
from the number on record as that church's pastor; a reply from any other
number is held as a draft for approval in the app.

How the code as deployed stands against that:

- **The condition holds, by the gate.** Only the one configured pastor number
  can reach the reply and SAVE path at all. A text from any other number never
  gets there, so nothing from another number is saved, as a draft or
  otherwise.
- **Not built: the draft for another number.** There is no second number that
  can reply to a visitor today, so there is nothing to hold. It becomes real
  the day more than one person at a church can answer.
- **Not built: naming who saved it.** The ruling says a save is credited to the
  pastor the number belongs to. The code leaves that empty, because the gate
  holds a number and not a person. It needs the pastor's number tied to their
  profile, which is the open question below.

Closed the same day by a second ruling (in the contract's rule 5, in his
words): there is no step where a pastor agrees to be texted visitors'
questions and no switch to turn it off; a published church is a church whose
pastor is reached. What remains is practical, not a permission: **which number
the app holds for each pastor.** A published church with no reachable pastor
is a fault in that church's setup, to show and fix.

One known rough edge: a pastor's reply that itself begins with the word "save"
would be read as the command if they had replied to something in the last day.

- **Not carried over:** their trial kept pastor-saved answers and reused them.
  When this was first written there was nowhere to keep one. There is now: the
  table `org_standing_answers` and its reader
  `org_standing_answers_in_force(church, today)` are on the live database
  (checked read-only 2026-10-13: both exist, the migration is in the live list,
  and the server role may read, add and change but not delete). The migration
  file's own header still says "NOT APPLIED"; that line is stale, and it is in
  the Telechurch repo, so it is reported to that side and not edited here.

  What it opens for this door, none of it built:

  - **Reading.** The relay already holds the server role in that same
    database. It could ask for a church's answers in force and hand them to
    the collector beside the cards, so a pastor's saved answer is used the
    moment it is saved. An answer past its end is not returned, which is the
    lifespan rule kept for free.
  - **Saving from a text.** The table has a place for it: an answer whose
    source is `reply` and whose status is `draft`, which is never given to a
    visitor until approved. So "save this" by text could write a draft and
    leave approval to the app. Whether the text door may write there at all,
    and whether a pastor's texted "SAVE" counts as approval, is not decided
    and is not this door's to decide.
  - **A gap.** A saved answer records which signed-in person saved it. A text
    has only a phone number. Tying the pastor's number to their profile is
    the same unsolved matching as section 2 of the design.

## What the relay now does, for the gated numbers only

1. A text from the visitor test number is written down as a question. Nothing
   is sent yet. (`RESET` and the consent words keep their old meaning.)
2. A collector asks for the next question and is given the words, the church,
   and whether it is a first text. Never the number.
3. The collector hands back an answer or a handoff.
   - An **answer** is sent to the visitor unchanged. An answer that names no
     saved fact is refused and treated as a fault.
   - A **handoff** is sent to the visitor unchanged, the pastor test number is
     told, with the question and a short number, and the question stays open.
   - On an urgent handoff the crisis line is added only if it is missing.
4. The pastor's reply to that text goes back to the visitor, "From the pastor
   of Canary: …", and the question closes. With several open the pastor starts
   with the number; a reply that cannot be placed is asked about, never guessed.
5. If no answer comes within 90 seconds, the next phone pulse sends the
   contract's fixed sentence and hands the question to the pastor.
6. If the pastor has not replied after the limit (24 hours, a setting), the
   visitor is told once and the pastor is reminded at the same moment.

Every text this path queues goes through one function that refuses any number
outside the gate.

Questions are kept as a new kind of record in the store the relay already
writes everything to (`alliance_records`, kind `sms_guide_question`). Checked
read-only on the live database: it is a plain table with no rule about kinds,
and its mirroring triggers ignore a kind they do not know. So this needs no
change to the database's structure. It does write rows. INFERRED that rows are
within "no change to the live database overnight"; his to overturn.

## What the gate test proves, and does not

Proves, on the source: for a number outside the gate, the previous relay and
this one make the same requests and give the same replies, text for text,
across twenty kinds of message. With the gate's settings absent, the test
numbers are ordinary numbers again. Inside the gate, each step above happens,
and a record planted with an outside number cannot be texted.

Does not prove: anything about the deployed function, the real database, the
phone, the model, or a real text. Those are exactly the steps that did not run.

Known gaps in the code as written:

- A question can be stranded if the relay fails between taking an answer and
  sending it. It would sit marked "answering" and nothing sweeps that state.
- The pastor's test number is also the relay's old test phone. When nothing is
  open for the pastor, a text from it takes the old path, as before.
- The pulse does two extra reads a minute while the gate is set.

## INFERRED, for the operator to overturn

- Rows in the existing record store do not count as a change to the database.
- The pastor's notice carries the visitor's words and never the visitor's number.
- The pastor's reply goes out as "From the pastor of {church}: …".
